# 对象审查与进一步审查

## 对象范围、调查重点与固定交付

- **确认目标身份：** 先确认用户给出的身份：绝对路径、软件名称与版本、服务名、任务路径、进程 PID 或系统入口。通过当前会话已有证据消除歧义；同名不同版本、商店版与桌面版、旧部署与当前版本分别定位。
- **固定交付五项：** 每个纳入本轮审查的对象始终交付**来源、用途、是否可以卸载或删除、处理影响、恢复与重建**五项。批量概览中按 [系统项筛选](system-exclusions.md) 默认排除的对象只作范围汇总，用户明确点名审查后适用这五项。用户强调的维度决定本轮补充调查的重点，不缩减交付维度；用户提出其他维度时再追加。已有证据仍有效时直接复用，缺少会影响判断的信息时补查。
- **深入审查与范围边界：** “详细检查、仔细看看、进一步审查”共用这五项要求。用户说“只查来源”时重点追查归属，其余四项仍给出当前有效结论与必要的未知说明。检查范围限于选定对象及解释其关系所需的证据；独立的新对象按批量规程列为候选。
- **编号指代与清理衔接：** 对固定编号的追问以记录中的成员路径为准。用户只选择集合内一个文件时，本次处理范围就是该文件；关联检查涉及的其他成员作为证据记录。明确要求卸载或清理时，复用审查结论，转入清理规程连续执行已有授权。

## 来源与用途要解释到什么程度

来源、用途是用户作出保留或清理决定的主要信息。分别回答，不能只把“缓存、配置、JSON、临时制品”等分类填进报告就结束。

### 来源

说明对象归属于哪个软件、工具、组件或工作活动，关键依据是什么，以及本机关系确定到了哪一层：

- **路径与命名线索：** 路径惯例或命名只能提示常见来源。例如某目录通常属于云工具的配置位置，不能据此确认本机由谁创建。
- **元数据与登记确认：** 产品元数据、配置、登记或引用一致时，可以确认相应软件归属；将产品名称与用户能识别的用途关联起来。
- **运行与读写确认：** 实际读写、日志或创建记录可进一步确认当前使用者或生成入口。已确认归属与已证明当前使用分别表述，证据不足时不推断具体创建进程。
- **来源未确定时的表达：** 来源未确定时，写清已确认的数据性质、归属线索、缺少的关键关系，以及这会限制什么判断。围绕能改变用户决定的线索进行有范围的追查。文件较小、目录为空或已知道文件格式，不降低用户关心来源时这个问题的优先级。

### 用途

- **关联实际功能与场景：** 用用户能理解的实际功能串起“谁使用这些内容、用于什么操作、目录承担什么作用”。说明用户在什么使用场景中可能需要它，区分原始资料、工作状态和可生成内容。
- **区分数据性质与消费功能：** 例如，“保存操作历史记录”说明了数据性质，还需确认所属工具拿这些记录做什么：是否用于统计展示、历史查看或其他实际功能。未查清消费这些数据的功能时，明确功能关系仍待确认，避免把可能用途写成事实。
- **组件与技术细节位置：** 组件名称需要必要的功能解释；结构、字段、版本、数量和时间戳放在它们能够支撑的结论后。来源和用途讲清之后，用户才能判断自己是否还需要相应功能或数据。

## 建立身份与关系

按问题组合读取对应专题；选择可能改变本次结论的查询。

1. **查看静态属性与签名：** 查看路径、类型、直接内容、版本元数据及必要签名信息，识别软件或文件线索。只读检查待审文件；读取脚本作为文本，发现的程序、脚本、安装包不作为探测命令执行。
2. **关联系统登记与实例：** 关联卸载登记、包身份、启动入口、运行实例或已知配置。比对完整路径、版本、发布者、产品标识和引用目标；仅厂商或关键词相同不足以认定为同一个软件。
3. **沿实际引用链补查：** 任务到脚本再到负载，快捷方式到参数或协议，宿主到调用程序，共享目录到具体组件。记录“谁以什么方式使用什么”，解释它支持的功能。
4. **甄别用户资料与共享关系：** 检查是否承载用户资料、是否由现有版本或其他产品共享。第二份可执行部署、后台维护入口和失效的包装入口按各自身份解释。
5. **收敛五项结论与缺口：** 把证据整理为固定五项结论。仍有影响判断的缺口时，给出条件性结论和具体待确认问题，不把“已交付报告”当作所有关系均已查明。

- **解析与覆盖缺口说明：** 只读脚本输出是候选证据。服务 `PathName`、卸载命令和带参数目标保留原文后按对应语法解析；带空格路径不能直接按空格取第一段。访问被拒绝、组件不可用与扫描截断都属于覆盖缺口。

## 五项分别回答什么

| 固定标签 | 回答要求 |
|---|---|
| 来源 | 软件、工具或工作活动归属，必要依据，已确认层级与归属缺口 |
| 用途 | 支持的实际功能、使用场景、内容的作用，以及与用户软件或操作的关系 |
| 是否可以卸载或删除 | 对应正式入口或适合的处理方式、可处理的精确范围、保留成员及判断条件 |
| 处理影响 | 软件功能、其他组件和用户资料会发生什么变化；区分已知后果与尚未确认的应用行为 |
| 恢复与重建 | 什么可自动生成或重新获取、所需前提、原配置和历史数据的恢复条件 |

- **恢复与重建的区分判断：** “可以重装程序”“缓存会重新生成”“原有数据能够恢复”分别判断。例如数据库结构可重建，原来的记录仍可能无法恢复；下载资源要说明可取得的来源和条件。尚未操作时，恢复条件用条件句表达，不暗示已有备份或回收站副本。

## 结论强度与待确认问题

| 可用证据 | 合适的表达 |
|---|---|
| 路径、产品元数据与登记或实际引用一致 | “已确认属于……，用于……功能；依据是……” |
| 多条线索一致，关键引用尚缺 | “较可能属于……；尚需确认……，这会影响……” |
| 只有名字、时间或泛化关键词 | “具体来源待确认；当前线索是……” |
| 指定范围完整查过且无匹配 | “在……范围内未发现……引用” |
| 部分查询失败或被截断 | “已确认……；……未覆盖，因此这项判断仍有限制” |

- **历史记录与特殊入口：** 旧日志、MRU、兼容性缓存和浏览器历史可证明曾经使用；结合当前登记、运行状态与可执行文件判断现状。没有找到文件不自动等于对应系统入口无效，例如协议快捷方式和 PWA。
- **待确认问题记录：** 各维度可以有不同确定程度。已知删除会丢失某些文件，并不代表已知这些文件对应用功能的作用。来源或用途仍是关键缺口时，记录到当前会话的待确认问题中，在相应项解释对建议的影响；下一步按用户关注点和可用证据决定。
- **复杂子目录边界：** 复杂子目录沿用批量规程的有限概览。在五项中说明当前已知内容、尚未审到的范围及判断限制，保持待单独展开状态；不为填满五项自动深入其后代。

## 进一步审查与交付

- **分批与追问复用：** 用户可选单个对象、整个集合、集合中部分成员或跨集合对象；超过 10 个集合时分批。重点追问可以增加对应项的解释深度，其他四项复用当前有效信息并补足必要缺口，不能用“同上”代替实际内容。新增维度按用户的问题追加。
- **版式与过程留存：** 采用 [交互指引](interaction.md) 中“一行对象标题＋五项连续无序列表”的版式，固定标签加粗。每项在对应条目内适度充分地解释，篇幅服从判断需要；默认不附完整查询过程。关键依据、真实限制与用户决策有关，写入对应项；命令、工具顺序、原始输出可按续查需要保存到任务记录。
- **交付前核对：** 五项是否齐全且集中在连续列表中；来源是否说明确定层级；用途是否讲清实际功能；处理与恢复条件是否有依据；待确认问题是否仍然可见。用户明确要求横向比较时，按交互指引采用比较表。将内容更新到报告和会话记录，再依据用户选择继续。
